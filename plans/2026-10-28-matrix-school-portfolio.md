## Stage 0 product frame — historical record

This section records the frame under which the existing calculator and landing
were built. It is preserved as factual project history, not current product
truth. The accepted current frame follows immediately after it and overrides
its old product journey.

### 1. Whose job and what trigger

When a hiring manager reviews a junior AI developer without commercial web
experience, they want compact, reproducible evidence of the complete working
process so they can decide whether the candidate can be trusted with real
projects.

### 2. Current alternatives and where they fail

- A résumé claim is fast but does not prove execution.
- A generic educational app proves some code but not domain research or a
  commercial web journey.
- A static themed landing page proves polish but little logic or verification.
- A standalone calculator proves logic but not the school/product context.

The combined educational landing and calculator closes all four gaps without
requiring a real client or fabricated outcomes.

### 3. Commercial threshold

Not applicable as a sellable product. This is explicitly a portfolio concept;
no customer economics or demand claims will be made.

### 4. Observable result

A reviewer could open the initial concept, calculate a versioned nine-point
matrix, inspect how one point was obtained, complete a compact lesson, and
reproduce the project’s checks from the public repository. A bounded AI school
consultant was planned but not implemented and is no longer in the active
product scope.

### 5. Format

A unique portfolio project, not a reusable commercial service. Calculation
rules and interpretation content remain separated so each layer can be tested
and replaced independently.

### 6. Registry location

The project lives only in this standalone folder and public repository. The
global knowledge project remains an internal methodology source and receives no
project implementation files.

## Current product frame after stages 1–11

### Product and audience

«Контур 22» is a fictional school of practical entry. Its seven-day
introductory mini-course «Первый разбор: попробуйте себя в консультировании» is
for a newcomer who has begun independent study, cannot yet turn separate values
into a coherent conversation, and wants to try the work before buying a large
program.

The result is one educational analysis, a 15–20-minute role conversation,
written curator comments, and a decision about further study. It is not a
professional qualification, client acquisition, income, diagnosis, prediction,
or proof of an objective symbolic system.

### Observable portfolio result

After the later implementation phases, a reviewer must be able to understand
the fictional offer, distinguish its business logic from implemented behavior,
complete a local demo registration with prepared data, see confirmation, change
or cancel it, inspect the preserved calculator, and verify the decisions and
tests in the repository.

### Two journeys

- Fictional business funnel: thematic material → landing → free lesson →
  decision about the mini-course.
- Real portfolio journey: employer's link → page → local demo registration →
  confirmation → change or cancellation.

The current page, calculator and browser-local demo are implemented. The bounded
boundary/data check passed locally and its results are accepted. There is no real lesson, registration,
email, payment, analytics, CRM, database, model API, or AI consultant.

## Challenge log

**Problem:** prove the exact capabilities named in the vacancy with one project
that remains small enough to finish and explain.

**Initial solution:** a fictional school landing page centered on a versioned,
explainable calculator lesson. A bounded AI consultant was planned as a future
secondary proof but never implemented.

**Current solution:** preserve the calculator as verified technical evidence,
but rebuild the product story around a seven-day practical mini-course and a
browser-local demo registration for its free lesson. This adds a coherent
commercial journey without creating real school operations or personal-data
collection.

**Alternatives considered:**

1. Static landing only — rejected because it under-proves logic and testing.
2. Calculator only — rejected because it under-proves product structure and
   persuasive web design.
3. Calculator as a teaser/paywall — rejected because the pattern is already
   common and would imitate the closest competitor.
4. Full school platform — rejected because accounts, payments, LMS features,
   and backend infrastructure do not improve the hiring proof proportionally.
5. GitHub Pages plus a browser-side model key — rejected because static hosting
   cannot protect the credential.
6. GitHub Pages plus a separate Amvera API — rejected because the split adds
   CORS, deployment, and failure complexity without improving the proof.
7. Keep the calculator as the page's complete offer — rejected after the
   product review because it explains a mechanism but not a credible course,
   audience, outcome, or next action.
8. Add a real registration or webinar — rejected because it introduces
   personal data and operations that are unnecessary for portfolio proof.
9. Continue to the AI consultant before fixing the product — rejected because
   the model feature does not repair the offer and expands privacy, cost, and
   safety scope.

**Why the current solution is better:** the course offer and two funnels prove
product reasoning; the local registration proves state design, accessibility,
privacy, and frontend behavior; the preserved calculator continues to prove
domain logic and testing. No active acceptance criterion requires a model
provider, real contact, event, or backend booking system.

## Challenge loop

### Does this solve the problem?

The accepted direction covers research, offer design, a complete local
interaction, the existing calculation core, visual craft, automated tests,
responsive/accessibility QA, public Git history, and factual Codex evidence. No
acceptance criterion depends on a real customer, real event, real contact, or
invented commercial result. The updated page and demo are implemented and the
bounded boundary/data check passed locally; final release is not claimed complete.

### Is this the most efficient solution?

- The existing Astro + TypeScript foundation already provides content-led pages,
  typed client logic, tests, and a deployable build; replacing it would add risk
  without improving the new product contract.
- Demo registration can remain a small browser-local island with no new backend,
  dependency, API, or service.
- The Node adapter remains part of the approved existing stack, but the current
  primary journey does not depend on a server action or model provider.

### Is there code for code’s sake?

The planned AI consultant has been removed from active scope. Database,
authentication, payments, email capture, analytics, booking API, agent tools,
personal AI readings, additional calculators, blog, admin, webinar, and LMS
remain excluded. Each would increase build and review surface without improving
the accepted hiring proof.
